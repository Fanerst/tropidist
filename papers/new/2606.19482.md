## Code definition

Locators: Sec. IV ("Directional tile codes"), Definition 1, Fig. 1(b),(c), Fig. 6; Sec. III with Algorithm 1 and Fig. 4. In 2504.09171: "Systematic construction of tile codes", conditions (T1)–(T2).

- **Directional word.** A word `D = d_1 … d_w` uses the letters N, E, S, W; exponents repeat a letter, so `N²ESEN²` is NNESENN. Read as a lattice path from a start vertex, it traverses `w` edges. These edges are the support of the X check. Data qubits sit on edges, written `h(i,j) = (i,j)–(i+1,j)` and `v(i,j) = (i,j)–(i,j+1)`. A step N from `(x,y)` traverses `v(x,y)`, E traverses `h(x,y)`, S traverses `v(x,y−1)` and W traverses `h(x−1,y)`. The strings are the supports and also the measurement walks: Sec. II and Sec. III make this point.
- **Tile.** A tile is the string translated into its box `[0,Bx−1]×[0,By−1]`, so that the box has no support on its top row or right column (T1). The box's lower-left vertex is the anchor. The Z tile is fixed by the mutual condition (Sec. IV; (T2) of 2504.09171): an X edge `h(a,b)` maps to the Z edge `v(B−1−a, B−1−b)`, and `v(a,b)` maps to `h(B−1−a, B−1−b)`. This is a point reflection that sends the primal lattice to the dual lattice. For a palindromic word it is the same word walked on the dual lattice, which is what Sec. IV's "directional pair" requires. App. A, last paragraph, notes that non-crossing open strings need palindromes. All words in the paper are palindromes. The module asserts that the reflected tile equals the dual walk of the same word. That dual walk starts at the plaquette SE of the X start for the four square-grid words, and at the plaquette NW of it for the hexagonal word.
- **Parity condition (Definition 1).** Every displacement vector with odd vertical displacement must occur an even number of times. A displacement vector runs from an edge of the ordered string to a later edge (Fig. 6). This guarantees a deterministic Algorithm 1 and is a simplified form of Theorem 1, Layout 1 of Gehér–Byfield–Ruban. Read in half-lattice units, the hardware grid, the condition holds for all six words below; a non-palindromic test word fails it.
- **Paper's box.** The paper writes a square `B×B` box. The module uses the tight `Bx×By` box. Both give identical codes and identical check counts for every word and every size tested (1..9 × 1..9).
- **Layout.** Bulk anchors carry both an X tile and a Z tile. X-only boundary anchors sit in `By−1` rows below and `By−1` rows above the bulk, in the bulk columns. Z-only boundary anchors sit in `Bx−1` columns left and `Bx−1` columns right, in the bulk rows (Fig. 1(c); the tile-code layout). The edge arrays are the union of the bulk boxes, every vertex with its right edge and its up edge. Boundary supports are truncated to the arrays.
- **Pruning (Sec. IV).** Edges contained in tiles of at most one type are removed. Checks whose support becomes empty are then removed. The remaining edges are the data qubits. No other modification of the code occurs: routing optimisation is accepted only if every stabiliser keeps its exact data support (Sec. V; App. C).
- **Orientation of the logicals.** X logicals run between the bottom and top sides, which carry the X boundaries. Z logicals run left to right. So `d_X` grows with `M` and `d_Z` with `N` (Sec. IV and Table IV; Fig. 9 draws X logicals vertical and Z logicals horizontal). On the 18-qubit code of Fig. 5, an exhaustive check gives `d_X = 3`, attained by a vertical X string, and `d_Z = 2`, by a horizontal Z pair. This matches the caption's `[[18,2,dx=3,dz=2]]`, so the paper's `d_X` is the weight of the lightest X logical, the `dx` of `planar_common`.

## Size convention (M, N): text versus tables

The prose of Sec. IV refers to "the vertices of an M×N subgrid" and to an `(M+B−1)×(N+B−1)` grid. The proof of Lemma 3 assumes `MN` bulk anchors. That reading reproduces none of Table III's sizes. The tables and figures instead use the following convention: `M×N` counts the **cells** of the anchor subgrid, so `(M+1)` **rows** (y) × `(N+1)` **columns** (x) of bulk anchors. The edge arrays are then `(N+Bx) × (M+By)` vertices. The evidence for this convention:

- Table III gives `(M,N)` and `n` for every row. All four printed rows are reproduced: (22,3) → 259 and 269; (19,4) → 365; (12,13) → 537. So is the commented-out `w=13` row of the TeX, `N²E³SESE³N²` at (16,9) → `n=611, k=20`. Swapping M and N fails.
- Table III's routing column (87, 196, 216) equals Table IV's affine `n_r` formulas evaluated at Table III's `(M,N)`. The formulas are asymmetric in M and N, so this fixes their order.
- Example 4's 346 unoptimised and 165 optimised routing sites for `[[323,14,15]]` equal Table IV's `ñ_r` and `n_r` at (M,N) = (5,16).
- The routing counts plotted in Fig. 8 solve Table IV's two formulas with integer `(M,N)`. They give exactly the sizes below, and those sizes give the paper's `n`.
- Data / X-check / Z-check counts are reproduced exactly for three figures: Fig. 1(b) `[[60,4,5]]`, 60/28/28; Fig. 3 hexagonal `[[52,10,3]]`, 52/22/20; Fig. 5 `[[18,2]]`, 18/6/10. In Fig. 5, 15 of the 18 drawn data sites coincide with ours. The other three are boundary qubits moved by one hardware site, which the routing optimisation does through data-start shifts. Fig. 3's data rows are our pattern rotated by 90°, again up to such shifts.

## Distances: what the paper states

- The paper states a distance method in one place only, the caption of Table III (App. B). That caption describes the authors' brute-force search over words and sizes with `M+N ≤ 25`. Distances were computed by integer programming. Above 20 the IP did not terminate, and QDistRnd upper bounds were used instead; those are the "≤" entries. Accordingly the module marks `d = d_Z` of Table III as `exact`, and notes that `dx` there is only an upper bound.
- For Tables II, V, VI and the figure examples the method is not stated, so `d_kind = "unknown"`. All these values are ≤ 15, so under the authors' pipeline they would presumably be IP values. Fig. 5's `dx=3, dz=2` was confirmed here by exhaustive enumeration; this was the only distance computation done.
- Fig. 8 places the Table II/V/VI square-grid sizes on a "uniform distance `d = d_X = d_Z`" axis, which suggests `d_X = d_Z = d`. The module still leaves `dx, dz = None` for these codes, because Table IV's linear fits (marked ≃) do not support exact uniformity everywhere. For `w=11` at (2,6) the fits give `d_X ≈ 7.7` and `d_Z ≈ 5.9`. At (5,16), the `[[323,14,15]]`, they give `d_X ≈ 13.4`, which is below the claimed 15. Worth checking with the exact runs.
- No circuit-level (fault) distance is reported anywhere. Performance is given only as logical error rates.

## Circuit-level information

Locators: Sec. III, Algorithm 1, Fig. 4, Fig. 5, the equations after Algorithm 1; Sec. V; App. C, Example 4, Fig. 7; App. E, Table VI, Table VII, Fig. 2.

- **Gate.** The primitive is `CXSWAP = SWAP·CX`, locally equivalent to iSWAP. The paper gives the identity `CXSWAP = (S†⊗HS†) iSWAP (H⊗I)`. An X check acts as control on data. Data acts as control on a Z check.
- **One round (Algorithm 1).** X checks are prepared in `|+⟩` and Z checks in `|0⟩`. For each letter `d_i`, every check moves one hardware site in direction `d_i`. It applies CXSWAP if the site holds data and SWAP if it is a routing site. Routing qubits then SWAP with data lying in direction `d_i`. All data qubits therefore drift by `−d_i` per step, and a check meets the data qubit on the `i`-th edge of its string at step `i`. The module stores this order as `x_order` and `z_order`. Checked: in every instance each data qubit meets at most one check per step. Routing SWAPs are also CXSWAPs, with the routing qubit prepared in `|0⟩` when it is the control and `|+⟩` when it is the target. Depth is `w`, or `w+2` with preparation and measurement. Successive rounds alternate the word and its inverse, which restores the layout. Fig. 5 adds boundary scheduling: a qubit is reset just before its first use and measured right after its last interaction.
- **Routing optimisation** (Sec. V, App. C, Fig. 7). Two heuristics are used: "route-window shortening" (shift a check's start along its walk to skip inactive prefixes or suffixes) and "trace pruning" (greedy deletion of edge routing sites with shifting). Data-start shifts onto former routing sites are allowed. A candidate is accepted after two simulated rounds, forward and backward, if supports, detectors and observables are unchanged and the detector error model is deterministic. The smallest valid candidate is kept. The resulting counts are fitted by Table IV's affine formulas `ñ_r` and `n_r`. Example 4 gives 346 → 235 → 165 sites for `[[323,14,15]]`.
- **Simulations** (App. E). Stim is used, with `d` rounds, CXSWAP-compiled circuits and `p = 0.001`. Table VII's uniform model puts depolarising `p` on two- and one-qubit Cliffords and on idles, and flips with probability `p` on resets and measurements. Decoding uses VibeLSD (an ensemble of serial min-sum schedules plus localised-statistics post-processing, LSD-0 fallback), with up to 10⁷ shots or 30 failures. The detector error models include routing-qubit detectors, used as flags. Rates are per logical qubit per round, averaged over the X and Z bases. Leakage is not modelled.
- **Rebuildability in Stim.** The unoptimised walk is fully determined by the word, the layout and Algorithm 1; the module's per-check step order suffices for the check schedule. Two details are missing. The standard layout's routing sites are described only qualitatively, as inserted where needed; Table IV's `ñ_r` can validate a reconstruction. The routing-qubit reset and measure timing, and hence the flag detectors, are not specified. The routing-optimised circuits behind every LER come from a heuristic search with candidate selection and cannot be reproduced exactly from the text. No circuit files or code are published.
- **Fault spreading.** The paper notes only that each data or check qubit takes part in at most `w` two-qubit interactions per round (citing Lemma 2). Hook errors and circuit distance are not analysed.

## Open questions the paper flags

- Distances above 20 are only upper-bounded (QDistRnd): every `d_X` entry of Table III.
- The numerical evidence is finite-size and covers few words. Broader searches over words, layouts, schedules and routing may find better instances. Code switching between words is suggested (Sec. VI).
- The noise model is simplified. Biased, coherent and hardware-calibrated noise are not studied, and neither is leakage. The decoder was not tuned to these circuits.
- The cost of logical operations under planar NN constraints is left open: lattice surgery, the reflection automorphisms of palindromic words, derived automorphisms, and the automorphism groups of Table V.

## Recorded ambiguities and assumptions

- **M, N convention.** The text and the tables disagree; the module follows the tables (see above). Under the text's reading Table III is not reproduced.
- **`[[74,10,4]]` (hexagonal, Table VI) is not reproducible.** For this word `2n+1 = (2M+9)(2N+5)`, and `149` is prime, so no rectangular patch has `n = 74`; no rotation or reflection of the word reaches it either. Other placements of the Z tile relative to the X tile were tested as well. They either break commutation or give a k that varies with size. Two of them reach n = 74, but with k = 6 and k = 9. The module builds (M,N) = (4,2), n = 76, as `dtc_hex_74_10_4` (flagged MISMATCH). This size continues (3,1) → (5,3), and it is the M↔N mirror of the square `w=9` `[[76,10,4]]` at (2,4); both families satisfy the same n formula with M and N exchanged. A typo 74 for 76 is plausible but unconfirmed. Other nearby sizes are n = 73 at (6,1) and n = 77 at (11,0).
- **Hexagonal sizes are not given.** `[[104,10,5]]` occurs at (5,3) and (1,7), and `[[199,10,7]]` at (6,7) and (5,8). All four are built. The Fig. 2 circuit-qubit counts (~294 and ~522) cannot separate them without the routing counts. The distance runs should show which size gives the claimed `d`.
- **`w=9` circuit-qubit offset.** The paper's `n_circ` for `w=9` (Fig. 2; Fig. 8 bottom; "exact" quadratic fit for `d ≥ 4`) exceeds data + checks + Table IV routing by 8 at every size. For `w=7` and `w=11` the counts agree. Our checks are all independent and none is left empty. With n and k equal, any extra checks in the authors' layout must be redundant, so the code is unchanged. The source of the 8 is not identified: the number of tiles emptied by pruning grows with size, so it is not that.
- **v1 versus v2.** The task description lists `[[60,4,5]], [[180,4,9]], [[217,10,7]], [[351,10,9]], [[182,14,10]], [[323,14,15]], [[248,20,11]]` as Table II. v2's Table II instead has `[[162,10,6]]`, `[[241,14,12]]` and the hexagonal `[[52,10,3]]`, `[[199,10,7]]`. Of the listed codes, `[[182,14,10]]` is in Table VI and `[[217,10,7]]` appears only as a Fig. 8 point (`figure_instances()`). `[[248,20,11]]` does not appear in v2. The `w=13` word `N²E³SESE³N²` survives only in a commented-out Table III row (`[[611,20,≤84,7]]` at (16,9), reproduced as n = 611, k = 20). With this construction it gives `n = 248, k = 20` at (M,N) = (5,9), (3,15) or (2,20). It is not built, since v2 does not report it. `directional_tile_code("N2E3SESE3N2", M, N)` builds any of these.
- **Positions.** `xy` are the unoptimised lattice positions: edge midpoints, with the hardware grid at half spacing. The optimised layouts shift a few boundary data and check qubits by one hardware site (Figs. 1(b), 5, 7). This does not affect the code.
- **Rotated surface codes** are included as `rsc_*` because they are rows of Table VI. They are baselines, not directional tile codes. The 4-CX and 4-CXSWAP rows use the same code.
