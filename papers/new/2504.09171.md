# Tile codes — extraction from arXiv:2504.09171

Source: Steffan, Choe, Breuckmann, Pereira, Eberhardt, "Tile Codes: High-Efficiency Quantum Codes on a Lattice with Boundary" (arXiv:2504.09171; published as PRL 135(17), 2025, doi:10.1103/l4mx-l3xx, per the bibliography of arXiv:2607.05897). These notes record the definitions used by `papers/planar_tile.py` (instances named `tile_*`). Only the paper's TeX source and PDF were consulted. The tile coordinates were machine-parsed from the TikZ code (`\horizontalqubits`, `\verticalqubits`, `\horizontalqubitsz`, `\verticalqubitsz`, `\boxsize`), not read off the rendered figures.

## Construction

Locators: the main text's run-in sections "Tile codes" and "Systematic construction of tile codes" (conditions (T1), (T2)), Fig. 1, "Examples of tile codes"; Appendix A with Fig. 2.

- **Qubits** sit on the edges of the square lattice. The builder labels a horizontal edge `h(x,y) = (x,y)-(x+1,y)` and a vertical edge `v(x,y) = (x,y)-(x,y+1)`, at positions `(x+0.5, y)` and `(x, y+0.5)`.
- **Tile (T1):** a set of edges of a `B x B` box. The edges on the box's top line and right line are excluded, so a tile uses `h(x,y)` and `v(x,y)` with `0 <= x, y < B`. The marked dot (the anchor) is the box's lower-left corner.
- **(T2):** the Z tile is determined by the X tile. An X edge `h(x,y)` corresponds to the Z edge `v(B-1-x, B-1-y)`, and an X edge `v(x,y)` to the Z edge `h(B-1-x, B-1-y)`. This makes X and Z tiles overlap evenly at every relative offset. All 21 tile pictures in the source satisfy (T2), so the builder takes the Z tile from (T2) and never needs a separately transcribed Z tile.
- **Layout:**
  - The bulk anchors are a rectangle of `l x m` points; the instances with parameters all use the unrotated square layout. A rotated (diamond) bulk set is also drawn, but no parameters are given for it.
  - The qubits are the union of the `B x B` boxes over the bulk anchors. That gives `(l+B-1) x (m+B-1)` horizontal edges and the same number of vertical edges.
  - Boundary anchors: `B-1` rows of X-only ("red") anchors below and above the bulk, over the bulk x range; `B-1` columns of Z-only ("blue") anchors left and right, over the bulk y range.
  - Checks that stick out of the layout are truncated to it.
  - Boundary commutation follows because boxes of opposite type meet only inside the layout (Fig. 1(c)).
- **Fine-tuning:** delete every qubit that lies in no X check or in no Z check, then delete the checks that became empty. One pass is enough, because removing a qubit never takes another qubit out of a check.
- **Builder checks:** the bulk X tile and the weight-3 boundary Z tile zoomed in Fig. 1(a,b) are present in the built `tile_288_8_12`. For the surface-code layout example, the builder gives exactly the 25 drawn edges and 12 + 12 checks. The builder's `tile_code` also accepts `Bx x By` boxes, which arXiv:2607.05897 needs. The argument is the same for rectangular boxes.

## How the distances were obtained

- **Main text ("Examples of tile codes"):** distances were first estimated with QDistRnd, a probabilistic GAP package, and then confirmed with an integer linear program. The Table I caption states that the tabulated distances are exact ILP values.
- **Search setup (Table I caption):** the unrotated square layout, `B`, `w` and `n` were fixed. A brute-force search over all tile configurations then picked the best `kd^2/n`.
- **Weight 6, 3x3 boxes:** the exhaustive search found that 12 is the best distance (main text). Appendix B says 16 tile pairs reach [[288,8,12]]. Table II draws 8 of them; the other 8 follow by swapping the roles of the X and Z tiles.
- **Weight 8, 3x3 boxes:** more than 300 pairs reach [[288,8,14]] (Appendix C). Table III draws 4.
- **Weight 10, B = 4:** no exhaustive search. A randomized search found [[512,18,<=23]]. The authors expect d = 23 but did not confirm it with ILP, so `d_kind = "upper"`.
- **d_kind for Appendices B and C:** the builder marks them "exact" because of the main-text workflow statement. The explicit per-code ILP statement exists only for Table I. For Appendix B this is moot, since all 16 codes are Table I row 1 (next section).
- **dx and dz:** the paper gives only `d`, so the builder leaves `dx = dz = None`. The exceptions are `tile_288_18_13`, `tile_512_18_19` and `tile_25_1_4_surface`, which are X<->Z self-dual (next section), so `dx = dz = d` there.

## Equivalences found here

These were checked with `planar_tile.isomorphic()`; rerun with `python papers/planar_tile.py --equiv`. The relabeling group is: each edge layer mapped by a symmetry of its 12x12 array (the 8 dihedral maps, chosen independently per layer), optionally exchanging the h and v layers, optionally exchanging X and Z. A hit proves equivalence; a miss proves nothing outside this group.

- **One weight-6 code:** all 16 weight-6 codes of Appendix B (drawn and swapped) are a single code up to qubit relabeling. So is the 12x12 member of the [[288,8,12]] family of arXiv:2607.05897.
  - Relative to `tile_288_8_12`, X and Z are exchanged (dx and dz trade places) for `b2, b3, b6, b7, b2s, b3s, b6s, b7s` and `bp288_288_8_12`. They are preserved for `b1, b4, b5, b1s, b4s, b5s, b8s`.
  - Computing dx and dz of `tile_288_8_12` therefore covers all 17. The field `same_code_as` records this.
- **Swapping X and Z tiles is always a relabeling in this layout:** exchanging the h and v layers combined with a 180-degree rotation of the arrays maps the code with X tile T to the code with X tile (T2)(T). So the caption's swap rule cannot produce new codes. Counted as codes rather than tile pairs, Appendix B contains one code.
- **Weight-8 codes:** the four codes of Table III (including Table I row 2) are pairwise inequivalent under the group.
- **Self-dual codes:** `tile_288_18_13`, `tile_512_18_19` and the surface code have a relabeling that exchanges X and Z, so dx = dz. No such map was found for any other instance in the builder.

## Circuit-level information

The paper has none: no syndrome-extraction circuits, schedules, circuit-level distances, thresholds or logical error rates. The Discussion leaves syndrome circuits to future work. It suggests adapting the BB-code cycle of Bravyi et al. and studying how the boundaries affect simulations and thresholds. No code, data or circuit files are referenced.

## Open questions the paper flags

- Whether the weight-10 [[512,18,<=23]] code really has d = 23. The authors expect it but did not verify it with ILP.
- Searches for weights above 8 were not exhaustive. Rotated layouts gave worse parameters; no numbers are given.
- Future directions: other bulk layouts (rotations, holes, polygonal boundaries), logical gates, adapted syndrome cycles with boundaries, and non-CSS (Clifford-deformed, XZZX-like) variants.

## Recorded ambiguities and assumptions

- **B = 4 tiles (Table I rows 3–4):** the TikZ source has a commented author remark, "I have to fix this", next to these coordinates. The drawn tiles reproduce n = 288 / 512 and k = 18. If a computed distance disagrees with 13 or 19, the paper's transcription of these tiles is the first suspect.
- **Layout of the w = 10 code:** not stated. The builder assumes 13x13 bulk anchors, the same as [[512,18,19]]. That is the only square layout with n = 512, and no qubit is removed.
- **Swapped Appendix B pairs:** not drawn. The builder uses (X tile, Z tile) = (drawn Z tile, drawn X tile) with the same layout. By the equivalence above, they are the drawn codes anyway.
- **Surface-code example:** the figure draws X boundary anchors only below and Z only on the right. The builder's symmetric layout adds only checks that end up empty, so the code is the same.
- **Appendix A formula:** the two expressions for n differ by `(B-1)^2`. Removing the top `B-1` rows and left `B-1` columns of vertical edges, as the appendix describes, gives `n = lm + (l-deg a)(m-deg b)` and `k = deg(a) deg(b)`. The builder reproduces both, for `a = 1+x`, `1+x^2`, `1+x+x^2` and `1+x+x^3`. The first expression, `2lm - l(B-1) - m(B-1)`, omits the overlap of the removed row and column strips. No instance uses Appendix A.
